# Chunksmith Controllerの生成制御

Minecraft 1.21.1 / NeoForge 21.1.262 / Chunksmith 4.8.1 / Millénaire 9.1.0。サーバーの現構成に対応する実装仕様です。

## 責務

| MOD | 担当 |
| --- | --- |
| Chunksmith | 実チャンク生成、LOD生成・保存・再利用判断、native安全制御 |
| Maki Chunksmith Controller | リソースと実処理の観測、生成候補の投入待ち、並列数探索、停止・再開 |
| Maki Chunksmith Chunk Cache | 一時FULLの退避、検証、読込、プレイヤーへの引渡し |
| Maki Millenaire Chunksmith Compatibility | 村候補の保留とMillénaireのキューへの再投入、建築準備の確認 |

自作MODは現構成のAPIを直接呼び出します。未導入時の実行経路や他バージョンへのAPI探索はありません。cacheはChunksmithの生成済み判定・LOD存在判定を変更しません。

## 候補と要求

ControllerはChunksmithの同心円iteratorから座標を一つ受け取ったところで、LOD・VALIDATE・FULLの候補WIPを予約します。枠が足りなければその座標を保持して待ちます。下流へ投入してから資源不足を理由に失敗Futureへ変えることはしません。

`isChunkGenerated`はnativeの結果をそのまま観測します。nativeの仮LODマークより前に、cacheのFULL所有権確認と生成受付を完了させます。確認I/Oの失敗は最大3回再試行し、その後はマーク前で打ち切ってWIPを解放し、座標を未完了として記録します。他の座標の受付を継続し、明示的な再開時には通常のChunksmith走査で再確認します。停止時もマーク前に取り消します。FULL＋LODが揃ってnativeがスキップする分岐は、そのまま通して追加のFULL検査を行いません。cacheの確認は保存・読込経路の処理であり、nativeの生成済み判定には反映しません。

要求ownerはticket safe pointにも引き継ぎます。停止epoch、プレイヤー優先、手動停止、外部タスクの所有権を維持します。

## 工程別WIP

| 工程 | 初期窓 | 最小 | 最大 | 目標待ち時間 |
| --- | ---: | ---: | ---: | ---: |
| LOD | 4 | 2 | 32 | 6秒 |
| VALIDATE | 4 | 1 | 16 | 6秒 |
| FULL | 2 | 1 | 8 | 8秒 |

開始済み工程の枠は実処理が終了したときに返します。論理タイムアウトやタスク停止だけでは返しません。LODはnative sinkへの受渡しから実書込終了まで保持し、native recordそのものの同一性でACKを照合します。ControllerはLODファイルを検証・無効化しません。

cacheはFULL検証と書込の実開始・実終了を通知します。FULL公開はLOD完了を待たず、アトミック公開の確定を別に通知します。

## 成果計測

同一試行tokenのLOD書込成功と、FULL公開またはFULL再利用の確認が揃った座標を、一度だけ総PAIR成果へ計上します。既存完成座標のスキップは計上しません。

| 成果 | 確認条件 |
| --- | --- |
| NEW | nativeが新規生成と判定した試行で、今回FULLを新規公開し、LOD書込も成功 |
| REPAIR | 既存FULLを確認・再利用した試行で、今回LOD書込が成功 |
| 未分類 | FULLを今回公開したが、force-load等によりnativeの新規生成分類が得られない試行 |

`fullPublished`と`fullReused`は別通知です。FULLの物理書込成功だけでは公開確定とみなしません。既存FULLの確認をNEWへ混ぜず、未分類をNEWと推定しません。別tokenの成果は合算しません。

探索目標は総完成PAIR/sを維持します。NEW/REPAIRの内訳と作業比率の変化を比較判定に使用し、ログには未分類を含む件数を分けて記録します。計測情報は既存FULL・LODの利用可否に影響しません。

## 並列数探索

初期上限はc=2。工程窓の調整を継続しながら、c±1を低頻度に比較します。評価窓30秒、settle 8秒、再試行間隔60秒を既定とします。実in-flightが変わらない、作業比率が変化した、工程窓が変化したなど、比較条件が成立しない場合は試験を採用しません。

CPU使用率の高さだけで減速しません。MSPT、GC、メモリ余力、OOM、CPU quota throttling、native幅、保存キュー、工程滞留を観測します。プレイヤー参加時には新規投入を止め、開始済み処理と保存・引渡しを完了させます。

Backfill生成器と専用の共有時間予算・予約API・設定・待機分岐はありません。cache自身の保存容量制限はcacheが担当します。

## FULLと村候補

cacheは通常FULLを優先します。cacheを借用するときは、実際のFULLファイルと所有権を検査します。生成済み判定を偽装したり、保存に失敗した座標の独立した生成再試行台帳を持ったりしません。

固定保存先IDと現存する旧schema 3のFULLを保持します。実チャンクの形式・座標・ディメンション・Entity・公開完了を検証します。MOD一覧、ワールド設定、将来の構成変更は監視しません。容量上限はFULL cacheに対するもので、LOD容量を合算・走査しません。

Millénaire互換MODはロード済みFULLとcacheの引渡し状態を読み取ります。再投入は毎20tick、最大8件で、現在のmain・孤立建築・SiteHunterキューの空きに制限します。MSPT・heap・GC・Chunksmithの生成幅・LODキューを使った独立した資源制御はありません。実際の建築予算と孤立建築のTTL・再試行はMillénaireに任せます。

## 実装と検証

生成投入、工程別通知、重複Mixinの整理、配布JARの更新は実装済みです。Gradle検査、上流ABI、Mixin注釈、MOD依存、配布ソース一致を検証します。

実NeoForgeサーバーでのMixin変換、プレイヤー移動、村建築、Entity/POI保存、再起動復元、A1上の性能比較は未実施です。

## 保存失敗と移行

一時FULLの保存ACKまではnativeチケットと要求の完了を保持します。容量不足・タイムアウトで保存が失敗しても、その座標のFULLを保持して保存を再試行し、Controllerの未完了試行を閉じません。cacheは保存の再試行だけを行い、新しいチャンクを生成しません。既に受け付けた要求はプレイヤー参加による新規受付停止と区別してdrainします。未ロードの借用ガードはプレイヤーへ引き渡しません。

通常の旧世代cacheは採用する保存元IDを先に原子的に記録し、ファイル単位の原子的renameで移します。旧データ全量の複製領域は要求せず、異なる正常FULLが衝突した場合は元を保持します。環境fingerprint監視は導入しません。


## 追加レビューで確認した境界

ControllerはFULLキャッシュ使用量・保存待ちbytesとChunksmithのLOD保存量を合算し、`generation-max-storage-bytes`（既定15GiB）で新規生成を止めます。LODの容量はnativeの公開store rootを非同期に読み取り、保存開始前のカウンタとの差分で計測後の増分を保守的に加算します。LODファイルの内容や妥当性には関与しません。Cacheの容量制限はFULL単独の保存容量として維持します。

事前に有効なFULLキャッシュを検出しても、通常FULLがなければ生成用の保存ガードを先に確保します。実読込に成功した場合だけ借用へ切り替え、`fullReused`を通知します。事前確認後の消失・破損時はガードを保持したまま生成FULLを保存します。

隔離FULLの任意復旧は、容量保留とその他のI/O障害を区別します。容量保留では、復旧済みの部分を読めるよう保存元IDを先に記録し、残りは隔離元に残して現行FULLの利用を継続します。プレイヤー引渡しのtick処理は座標ごとの失敗を記録し、保存抑止を保って20tick後以降に再試行します。

native LODの失敗ACKはControllerの未完了観測に残し、稼働中の範囲終了を`incomplete-pregen`として表示します。ただし、この記録は実行中の制御状態であり、LODの修復・永続的な再試行台帳ではありません。Chunksmith 4.8.1の失敗後の存在マーク修復、村の増改築後の既存LOD更新、クラッシュ後にLODだけ残ったHorizon座標のFULL補完は、Chunksmith側での対応が必要です。このPRではCache・Controller・Millénaire互換MODにLODの判定上書き、無効化、更新キューを追加しません。これらの指摘は修正完了として扱いません。

配布JARと上流タグの[本体コード確認結果](chunksmith-4.8.1-native-lod-audit.md)では、この3点が現構成に残ることを確認しました。既存LODの上書き能力自体は本体にあり、LOD書込失敗の存在ビットも再起動・LRU追い出し後には欠落を認識し直せます。HorizonのLOD優先スキップは本体の意図した仕様であり、FULL補完は今回のキャッシュ要件との統合課題です。3点を一律にChunksmith単体の不具合と分類しません。
